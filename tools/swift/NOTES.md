# Swift port notes (SwiftFormat 0.64.7)

## Layout

- `src/swift/token.ts` — token kinds, `SwTokList` (parallel kind/string/aux arrays), Token predicates.
- `src/swift/tokenizer.ts` — `tokenize()`, faithful to Tokenizer.swift.
- `src/swift/formatter.ts` — Formatter: edits, enumeration (`enumStart`/`enumNext` keep
  `forEachToken`'s index right across edits), scope-aware `index(of:after:)` / `lastIndex`,
  auto-updating ranges (`ref`/`unref`).
- `src/swift/parsing.ts`, `parsing2.ts`, `expr.ts`, `funcdecl.ts`, `modifiers.ts`, `decl.ts`,
  `imports.ts` — ParsingHelpers / FormattingHelpers / Declaration ports.
- `src/swift/rule_*.ts`, `rules_*.ts` — the rules.
- `src/swift/rules.ts` — rule names in SwiftFormat's order (index by name, then orderAfter).
- `src/swift/dispatch.ts` — generated by `tools/swift/gen_dispatch.py` from `tools/swift/rules.txt`.
- `src/swift/run.ts` — applyRules: trailingSpace+indent first, then every rule, up to 10 passes.
- `src/swift/directives.ts` — `swiftformat:` comment directives (processDirectives, rule names).
- `src/swift/unicode.ts`, `unicode_data.ts` — Swift Character semantics: grapheme clusters
  (String.count) and case tests; the table is generated by `tools/swift/gen_unicode.py`.

## Options

The CLI with no config infers nothing: `applyRules` only infers shared options that no enabled
rule owns (the sortDeclarations thresholds/locale), and none of those has an inferrer. Swift
version is undefined ("0"), so every `swiftVersion >= X` check is false and `< X` is true:
no if/switch expressions, no implicit self in closures, no trailing commas outside
collections, no implicit returns outside closures, and so on.

Per-rule comparisons with `swiftformat --rules X` differ in one way: with only X enabled, its
shared options (`indent`, `linebreaks`, ...) are inferred from the file. Compare those with
leading whitespace ignored (`LEADWS=1` in the scratch rulecmp script).

## Status

Corpus (`WORK=/work/out-swift2 bash bench/corpus/cmp.sh <bin> swift`): 6710 / 6710 identical.
Every default rule is ported (no guards left).

Timings on the corpus (6710 files): swiftformat 131.7 s wall on 4 cores, 262.5 s with
`taskset -c 0`; nishfmt 13.8 s with cmp.sh on 4 cores and 28.6 s with `taskset -c 0 ffk -i -q
-j 1` (best of 3), both measured on a shared, loaded machine (see Performance).

Ported rules: everything in `tools/swift/rules.txt` with a module other than `noop`.
No-op rules (`noop`) do nothing with the default options and an undefined Swift version.
The last three rules ported: redundantMemberwiseInit (`rules_memberwise.ts`),
noForceUnwrapInTests (`rules_unwrap.ts`, with parseExpressionRange(endingAt:) and
(containing:)), preferForLoop (`rules_forloop.ts`, String.singularized() through
`nish/regex`; a non-ASCII loop subject makes the file skip).

swiftTestingTestCaseNames lowercases the first letter of a renamed test ASCII-only; a
non-ASCII first letter makes the file skip (fatalError) instead.

A fatalError in a rule skips the file.

## Directives

`swiftformat:` comments work as in Formatter.swift: directives are parsed per pass
(`swProcessDirectives`, with the `next`/`previous` line shift), and `updateEnablement` is a
port of SwiftFormat's. Enablement reaches the rules the way it does in SwiftFormat:

- `enumStart`/`enumNext` are forEachToken (onlyWhereEnabled: true): they update enablement at
  `//`, `/*`, `*/` and linebreaks and skip disabled tokens. `enumStartAll`/`enumNextAll` are
  onlyWhereEnabled: false (indent, blankLinesBetweenScopes, linebreakAtEndOfFile).
- `swParseDeclarationsIn` leaves out declarations where the rule is disabled
  (`enabledInLoopAt`); parseEnclosingType's body uses the current state (`_useForEachToken:
  false`). parseImports enumerates, so hasImport / detectTestingFramework see directives.
- redundantSelf's helpers and headerCommentTokenRange make SwiftFormat's own
  `updateEnablement` / `isEnabled(at:)` calls; `insertSpaceIfEnabled` is `swApplyIndent`.

So a rule port must enumerate with enumStart wherever SwiftFormat uses `forEach`, even for a
read-only scan (noForceUnwrapInTests' test cases and `!`s, availabilityArgumentRanges).
Checked with `tools/swift/fuzz_directives.py RULE N FILELIST` (FILELIST: corpus files the rule
changes, e.g. from `swiftformat --lint`): directives (disable/enable, :next, :this, block comments,
the rule's name and `all`) inserted near the lines each rule changes in corpus files, about
4700 variants over every rule, all identical to swiftformat. `SW_DIRECTIVE_UNSAFE_RULES` in
directives.ts can list a rule whose directives should make the file skip (none now).

Not handled, the file is skipped: `options` directives (only the default options are ported),
`swiftformat:sort` comments (sortDeclarations is not ported), directive rule names that are not
ASCII. An unknown or empty directive is a fatal error in SwiftFormat too.

## Unicode

`swCharCount` (String.count) segments extended grapheme clusters per UAX #29 (GB3-GB13) from
`unicode_data.ts` (Grapheme_Cluster_Break and Extended_Pictographic from Perl's Unicode 15.0
tables). Checked against swiftformat's alignment on every assigned code point in `"aXa"` and
30 000 random 2-5 code point strings (`tools/swift/oracle_graphemes.py`; case data with
`oracle_case.py`). SwiftFormat's Swift 6.2 runtime has newer Unicode data,
so code points unassigned in Unicode 15.1 and viramas (GB9c, Indic conjuncts, depends on
them) set `SW_UNI_UNCERTAIN` and the file is skipped when one is counted or case-tested.

Case: `swCharacterUppercaseInvariant` (`String(c).uppercased() == String(c)`: redundantInit,
parseType's lowercase-identifier test) and `swCharacterIsUppercase` (isInResultBuilder) use
Python's Unicode 15.1 case data per scalar, over the whole first Character. `swLowercased` stays
ASCII: exact for the ASCII prefix/suffix tests it serves (see its comment); todos skips on a
Kelvin sign. Import sorting skips on non-ASCII module names, sortTypealiases on non-ASCII
type names. Where SwiftFormat's hasPrefix / dropFirst / first work on Characters and a
combining scalar would move a Character boundary (todos, spaceInsideComments, docComments),
`swUniCheckPrefix` / `swUniJoinsPrevious` make the file skip.

spaceInsideComments checks only the Character boundaries before bytes 1-3 of a comment body
(`swUniCheckPrefix(s, 4)`), the most its first / second Character and `hasPrefix("===")`,
`("---")`, `("**")`, `("*/")` can read. Checking byte 4 as well skipped swift-syntax's
`Syntax+Assertions.swift` on ``/// `1️⃣` that ...``, where U+FE0F sits at byte 4 of the body.
Keycap emoji are digit, U+FE0F, U+20E3; both marks are Grapheme_Cluster_Break=Extend in the
port's Unicode 15.0 table, so `swGraphemeCount` counts the sequence as one Character, and
`oracle_graphemes.py` checked each mark alone in `"aXa"`; spaceInsideComments never reads
the boundary after the digit anyway. `Syntax+Assertions.swift` now matches SwiftFormat
0.64.7 byte for byte. Regression cases `keycap_comment` and `keycap_block_comment`
(SwiftFormat 0.64.7 output) fail on the base binary, which skips them.
Guards, all skipped by the base and current binaries:

- `skip_comment_combining_prefix` (`//===` U+0301, where `hasPrefix("===")` is false
  Character-wise): fails with `swUniCheckPrefix(s, 3)` in the `//` loop.
- `skip_block_comment_combining_dashes` (`/*---` U+0301, `hasPrefix("---")` false
  Character-wise): fails with `swUniCheckPrefix(s, 3)` in the `/*` loop.
- `skip_block_comment_combining_space` (`/*! ` U+0301, whose second Character is not a
  space): fails with `swUniCheckPrefix(s, 2)` in the `/*` loop.

## Known differences

- Other ASCII `hasPrefix`/`hasSuffix` checks are byte-wise; SwiftFormat's are Character-wise,
  so they differ when a combining scalar follows the matched prefix (not seen in the corpus).
- Comment bodies shaped like `word: text` are comment directives to SwiftFormat (nestedIf,
  docComments honour that).

## Performance

Measured with `taskset -c 0 <bin> -i -q -j 1 <copy of raw>`, best of 3 (the machine was shared
and loaded, so compare builds back to back): 36.6 s with every rule ported (commit b47ac19),
28.6 s after the caching and scope-code commits. Profile with `nish tools/dev/swift.ts -g
--link devg` and `valgrind --tool=callgrind devg <file>` (one file), or the full binary with
`--trace-children=yes` (nishfmt formats in worker processes).

What is in place:

- endOfScope(at:) and the current scope (`index(of: .startOfScope, before:)`) and the last
  keyword at the current scope (`index(of: .keyword, before:)`) are memoised per mutation
  count; replacing a token with an equal one is not a mutation.
- parseDeclarations() is cached across rules while nothing changes (SwiftFormat does the same;
  `swReleaseDecls` keeps a still-valid cache), hasImport keeps the module names per mutation.
  Neither cache is used when the file has directives.
- Each token has a scope code (`SwTokList.c`, `swScopeCode`), so `indexInType`,
  `lastIndexInType` and `closes` compare integers (`swClosesByCode`, `swTokIsAt`).
- removeTokens moves the token arrays once; consecutiveBlankLines only looks for the enclosing
  scope inside multiline strings.

Still hot (in that order): scope-aware backward scans after an edit (`lastIndexInType` from
startOfScope / isInResultBuilder / indexOfLastSignificantKeyword: every edit invalidates the
memo, and a scan walks every token of the sibling blocks it passes; a per-END-token jump
offset kept up to date during the array shifts would make those O(siblings), but the scan's
`linebreakEncountered` / `case` / `:` quirks must be preserved), the element-wise array shifts
of insertAt/removeAt (four parallel arrays; `set` cannot block-copy `string[]`, and
`slice`+`set` was slower), `swParseType`'s forward scans, and isInStringLiteral (rebuilt from
scratch after every edit).
